# 요구사항 문서

## 소개

이 기능은 한국 주식 거래에서 초단위 스캘핑을 위해 설계된 특화된 임베딩 모델과 GRPO (Group Relative Policy Optimization) 강화학습 시스템을 도입합니다. 시스템은 고차원 매매 데이터를 컴팩트한 벡터 표현으로 변환하고, 이러한 임베딩을 사용하여 실시간 시장 상황에 기반한 빠른 매매 결정을 내릴 수 있는 GRPO 에이전트를 훈련합니다.

임베딩 모델은 60개 이상의 시장 지표를 밀집 벡터 공간으로 압축하는 특징 추출기 역할을 하며, 실시간 거래 중 빠른 추론을 가능하게 합니다. GRPO 알고리즘은 여러 거래 에피소드 간의 성능 비교를 통해 효과적인 스캘핑 전략을 학습하기 위해 그룹 기반 정책 최적화를 활용합니다.

## 요구사항

### 요구사항 1: 임베딩 모델 아키텍처

**사용자 스토리:** 거래 시스템 개발자로서, 다중 특징 매매 데이터를 컴팩트한 벡터 표현으로 변환할 수 있는 임베딩 모델을 원합니다. 이를 통해 스캘핑 결정을 위한 실시간 시장 데이터를 효율적으로 처리할 수 있습니다.

#### 수락 기준

1. WHEN 임베딩 모델이 60개 이상의 특징(등락률, 누적거래대금, 거래회전율, 체결강도, 매도/매수대기금액1-10, 종목명_scalar, 시간_sin, 시간_cos, 시간_scalar2)을 가진 매매 데이터를 받으면 THEN 시스템은 이를 고정 크기의 밀집 벡터로 인코딩해야 합니다 (임베딩 차원 설정 가능, 기본값 128-256)

2. WHEN 모델이 매매 데이터 포인트의 시퀀스를 처리하면 THEN 시스템은 단일 스텝 인코딩과 시퀀스 인코딩 모드를 모두 지원해야 합니다

3. WHEN 임베딩 모델이 훈련되면 THEN 시스템은 대조 학습(contrastive learning) 또는 오토인코더 기반 목적 함수를 사용하여 시간적 및 시장 역학을 보존하는 의미 있는 표현을 학습해야 합니다

4. WHEN 모델 아키텍처가 정의되면 THEN 시스템은 지역 패턴 추출을 위한 CNN 레이어와 중요한 특징을 포착하기 위한 어텐션 메커니즘의 조합을 사용해야 합니다

5. IF 모델이 추론을 위해 배포되면 THEN 시스템은 초단위 스캘핑을 지원하기 위해 CPU 혹은 GPU에서 샘플당 10ms 미만의 인코딩 지연 시간을 달성해야 합니다

### 요구사항 2: 빠른 추론 파이프라인

**사용자 스토리:** 거래 시스템 운영자로서, 임베딩 모델이 최소한의 지연 시간으로 실시간 매매 데이터를 벡터로 변환하기를 원합니다. 이를 통해 RL 에이전트가 스캘핑 작업 중 적시에 거래 결정을 내릴 수 있습니다.

#### 수락 기준

1. WHEN 실시간 매매 데이터가 도착하면 THEN 시스템은 훈련에서 캐시된 통계를 사용하여 데이터를 전처리하고 정규화해야 합니다

2. WHEN 임베딩 모델이 추론을 수행하면 THEN 시스템은 여러 종목을 동시에 배치 처리할 수 있어야 합니다

3. WHEN 모델이 로드되면 THEN 시스템은 계산 오버헤드를 최소화하기 위해 최적화된 추론 모드(torch.jit.script 또는 ONNX)를 사용해야 합니다

4. IF GPU를 사용할 수 있으면 THEN 시스템은 배치 추론을 위해 GPU 가속을 활용해야 하며, 그렇지 않으면 최적화된 CPU 실행으로 대체해야 합니다

5. WHEN 임베딩이 생성되면 THEN 시스템은 겹치는 시간 윈도우에 대한 중복 계산을 피하기 위해 최근 임베딩을 캐시해야 합니다

### 요구사항 3: GRPO 훈련 환경

**사용자 스토리:** ML 엔지니어로서, 스캘핑 전략을 위한 GRPO 훈련을 지원하는 커스텀 Gymnasium 환경을 원합니다. 이를 통해 RL 에이전트가 그룹 기반 정책 비교를 통해 학습할 수 있습니다.

#### 수락 기준

1. WHEN GRPO 환경이 초기화되면 THEN 시스템은 임베딩된 매매 시퀀스를 관측값으로 받아들여야 합니다 (원시 특징이 아님)

2. WHEN 에이전트가 행동(매수/매도/보유)을 취하면 THEN 환경은 스캘핑 특화 메트릭(거래당 수익, 보유 시간 페널티, 거래 비용)을 기반으로 보상을 계산해야 합니다

2.1. WHEN 거래 비용이 계산되면 THEN 시스템은 수수료(0.015%) + 세금(0.2%)을 합산하여 총 0.215%의 거래 비용을 적용해야 합니다

2.2. WHEN 보상이 계산되면 THEN 시스템은 수익률이 거래 비용(0.215%)을 초과하는 경우에만 양의 보상을 제공해야 합니다

3. WHEN 에이전트가 매수 후 설정 가능한 시간 임계값(기본값 1.5초) 이내에 가격이 상승하지 않으면 THEN 환경은 자동으로 매도 신호를 트리거하고 손실 페널티를 적용해야 합니다 (빠른 손절 룰)

4. WHEN 여러 에피소드가 수집되면 THEN 시스템은 그룹 상대 정책 업데이트를 위해 시장 상황(변동성, 추세 방향)별로 에피소드를 그룹화해야 합니다

5. WHEN 환경이 리셋되면 THEN 시스템은 다양한 시장 상황을 가진 DuckDB 데이터베이스에서 시작 지점을 샘플링해야 합니다

6. IF 에이전트가 설정 가능한 시간 임계값(기본값 60초)을 초과하여 포지션을 보유하면 THEN 환경은 빠른 스캘핑 행동을 장려하기 위해 증가하는 페널티를 적용해야 합니다

7. WHEN 에피소드가 종료되면 THEN 환경은 그룹 비교를 위해 에피소드 메타데이터(총 수익, 거래 횟수, 평균 보유 시간, 샤프 비율, 빠른 손절 룰 위반 횟수)를 기록해야 합니다

### 요구사항 4: GRPO 알고리즘 구현

**사용자 스토리:** ML 연구자로서, 그룹 상대 어드밴티지를 사용하여 정책을 최적화하는 GRPO 알고리즘 구현을 원합니다. 이를 통해 에이전트가 다양한 시장 상황에서 강건한 스캘핑 전략을 학습할 수 있습니다.

#### 수락 기준

1. WHEN GRPO 훈련이 시작되면 THEN 시스템은 현재 정책을 사용하여 여러 롤아웃(그룹당 기본값 8-16 에피소드)을 수집해야 합니다

2. WHEN 에피소드가 그룹화되면 THEN 시스템은 시장 체제 지표(변동성 분위수, 추세 강도)를 기반으로 클러스터링 또는 규칙 기반 그룹화를 사용해야 합니다

3. WHEN 어드밴티지가 계산되면 THEN 시스템은 각 에피소드의 수익을 그룹 평균 수익과 비교하여 그룹 상대 어드밴티지를 계산해야 합니다

4. WHEN 정책이 업데이트되면 THEN 시스템은 베이스라인 차감 어드밴티지 대신 그룹 상대 어드밴티지를 사용하는 PPO 스타일의 클리핑된 목적 함수를 사용해야 합니다

5. IF 정책이 참조 정책에서 크게 벗어나면 THEN 시스템은 안정적인 학습을 보장하기 위해 KL 발산 제약을 적용해야 합니다

6. WHEN 훈련이 진행되면 THEN 시스템은 그룹 수준 메트릭(그룹당 평균 수익, 정책 엔트로피, KL 발산)을 TensorBoard에 로깅해야 합니다

### 요구사항 5: 임베딩 모델 훈련 파이프라인

**사용자 스토리:** 데이터 과학자로서, 과거 매매 데이터로부터 학습하는 임베딩 모델의 훈련 파이프라인을 원합니다. 이를 통해 임베딩이 GRPO 에이전트를 위한 의미 있는 시장 패턴을 포착할 수 있습니다.

#### 수락 기준

1. WHEN 임베딩 모델이 훈련되면 THEN 시스템은 `C:\Users\user\Workspace\datasets@20251005\datasets_norm_all.duckdb` 데이터베이스에서 데이터를 로드해야 합니다 (테이블명: datasets, 인덱스: idx_datasets_code_date_time)

2. WHEN 데이터가 로드되면 THEN 시스템은 데이터를 훈련(70%), 검증(15%), 테스트(15%) 세트로 시간 순서를 유지하며 분할해야 합니다

3. WHEN 훈련 샘플이 생성되면 THEN 시스템은 긍정 쌍(동일 종목의 시간적으로 가까운 샘플)과 부정 쌍(다른 종목 또는 먼 시간대의 샘플)을 생성해야 합니다

4. WHEN 손실이 계산되면 THEN 시스템은 긍정 쌍의 유사도를 최대화하고 부정 쌍의 유사도를 최소화하기 위해 대조 손실(InfoNCE 또는 triplet loss)을 사용해야 합니다

5. IF 오토인코더 접근 방식이 사용되면 THEN 시스템은 임베딩에서 입력 특징을 재구성하고 재구성 오류를 최소화해야 합니다

6. WHEN 모델이 훈련되면 THEN 시스템은 설정 가능한 체크포인트 간격으로 체크포인트 저장 및 재개 가능한 훈련을 지원해야 합니다

7. WHEN 검증이 수행되면 THEN 시스템은 다운스트림 작업 성능(예: 고정된 임베딩을 사용한 방향 예측 정확도)을 사용하여 임베딩 품질을 평가해야 합니다

### 요구사항 6: 기존 시스템과의 통합

**사용자 스토리:** 시스템 아키텍트로서, 임베딩 모델과 GRPO 컴포넌트가 기존 stock-bot 인프라와 원활하게 통합되기를 원합니다. 이를 통해 기존 데이터 파이프라인과 API 통합을 활용할 수 있습니다.

#### 수락 기준

1. WHEN 임베딩 모델이 저장되면 THEN 시스템은 기존 모델과 동일한 체크포인트 형식(state_dict, config, feature_names, metadata를 포함하는 PyTorch dict)을 사용해야 합니다

2. WHEN GRPO 훈련 스크립트가 호출되면 THEN 시스템은 기존 RL 훈련 스크립트와 동일한 CLI 인수(--db, --table, --seq-len, --device, --out)를 받아들여야 합니다

3. WHEN 시스템이 데이터를 로드하면 THEN 시스템은 슬라이딩 윈도우 생성과 함께 ai_trader.ml.data의 기존 DuckDB 데이터 로더를 재사용해야 합니다

4. WHEN GRPO 에이전트가 배포되면 THEN 시스템은 실시간 거래를 위해 Kiwoom REST API 클라이언트(koapys.client.KoapyRestSimple)와 통합되어야 합니다

5. IF 임베딩 모델이 추론에 사용되면 THEN 시스템은 기존 지도 학습 모델과 동일한 정규화 파이프라인을 지원해야 합니다

6. WHEN TensorBoard 로깅이 발생하면 THEN 시스템은 표준 디렉토리 구조(models/{model_name}/tensorboard_logs)에 로그를 작성해야 합니다

### 요구사항 7: 모델 평가 및 모니터링

**사용자 스토리:** 거래 시스템 운영자로서, 임베딩 모델과 GRPO 에이전트 모두에 대한 포괄적인 평가 메트릭을 원합니다. 이를 통해 성능을 평가하고 정보에 입각한 배포 결정을 내릴 수 있습니다.

#### 수락 기준

1. WHEN 임베딩 모델이 평가되면 THEN 시스템은 임베딩 품질 메트릭(종목 클러스터링을 위한 실루엣 점수, 시간적 일관성 점수)을 보고해야 합니다

2. WHEN GRPO 에이전트가 평가되면 THEN 시스템은 스캘핑 특화 메트릭(승률, 거래당 평균 수익, 최대 낙폭, 샤프 비율, 평균 보유 시간)을 보고해야 합니다

3. WHEN 백테스팅이 수행되면 THEN 시스템은 현실적인 거래 비용과 슬리피지를 포함하여 홀드아웃 테스트 데이터에서 거래를 시뮬레이션해야 합니다

4. WHEN 에이전트가 실시간으로 거래하면 THEN 시스템은 타임스탬프, 진입/청산 가격, 보유 기간, 손익과 함께 모든 거래를 로깅해야 합니다

5. IF 에이전트의 성능이 저하되면 THEN 시스템은 설정 가능한 임계값(예: 낙폭 > 5%, 승률 < 45%)을 기반으로 알림을 트리거해야 합니다

6. WHEN 훈련이 완료되면 THEN 시스템은 훈련 진행 상황, 최종 메트릭 및 샘플 거래 에피소드를 요약하는 HTML 보고서를 생성해야 합니다
